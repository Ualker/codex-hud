运行 `npm run bench`。直接执行 `node scripts/benchmark-hud.mjs --build /absolute/path/dist --iterations 1000 --file-mib 32` 可对比独立构建。仅生成临时日志，不连接用户 tmux 或 Codex 服务；结束后删除临时文件。输出 JSON 包含每帧耗时、CPU、RSS、stdout 写入次数、子进程调用次数，以及四个长日志读取器的冷读、未变化复读和事件循环延迟。

四个读取器同时读取 32 MiB 日志：冷读 257 → 251 ms；RSS 均约 118 MiB；未变化复读 0.06 → 0.11 ms，处于极短采样区间，不据此宣称进退。事件循环 p95 12.09 → 11.98 ms。渲染改进来自复用准备好的布局计算高度，避免整帧格式化两遍。

行为门槛由回归测试约束：65 MiB 未读积压应分批前进到 EOF、坏记录之后继续读取、未变化日志直接复用缓存、真实按键/重载保持主 pane 存活。性能数字用于后续同机对照，不用脆弱的微秒级 CI 阈值代替行为验证。

## 2026-10-15：完整运行时基准

运行 `npm run bench:runtime`；参数示例：`node scripts/benchmark-runtime.mjs --instances 1,5,20 --seconds 12 --history-mib 8`。需要 tmux、Git 和 sqlite3。每组启动真实 HUD 进程、私有 tmux server、临时 Git 仓库和 SQLite 数据库；模拟主进程只运行 `sleep`，不调用 Codex，也不读取用户会话。每份合成 rollout 含约 8 MiB 历史，测量期间每 200 ms 追加一次状态，每组共 59 次。日志模式为 WAL，与本机 Codex 的 logs/state 数据库一致。

本机 macOS arm64、Node v24.21.0；测试套件结束后单独采样，包含冷启动、进程绑定、SQLite、Git、watcher 和 Overview。原始汇总见 [performance-2026-10-15.json](./performance-2026-10-15.json)。

| 并发 HUD | 累计 CPU ms | 结束 RSS 合计 MiB | 各进程峰值 RSS 之和 MiB | 事件循环 p95 ms | 最大停顿 ms | tmux / ps / Git 调用 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 303.55 | 72.98 | 89.89 | 11.12 | 35.09 | 10 / 1 / 1 |
| 5 | 2783.46 | 524.78 | 585.13 | 11.33 | 42.14 | 45 / 5 / 5 |
| 20 | 13590.21 | 1896.03 | 1998.50 | 11.54 | 81.26 | 153 / 20 / 20 |

三组分别执行 180 / 900 / 3600 条原生 SQLite 语句，失败和超过 50 ms 预算的次数均为 0；最慢语句分别为 0.42 / 0.39 / 5.64 ms。早期 rollback-journal fixture 的一次 20-HUD 运行出现过单次查询失败，复测未再出现；未取得那次错误码，不能断言其原因或把切换 WAL 后的变化当成代码优化收益。诊断现保留最后一次 SQLite 错误码，不记录 SQL 字面量。

解释这些数字时需要保留以下边界：

- CPU 是 HUD Node 进程的累计消耗，不包含子进程 CPU；每个进程的测量包含自己的启动过程，不能直接换算成稳定态占用率。
- RSS 按进程求和，包含共享页；峰值之和也不是同一时刻的全机峰值。20 个 HUD 仍接近 2 GiB，长期大量并发仍有独立 Node 进程的内存成本。
- 事件循环采样分辨率为 10 ms，表中 p95 取各 HUD p95 的最大值；最大停顿另列，避免平均数遮住冷启动尾延迟。此前非 WAL fixture 的单次采样曾出现约 384 ms 停顿，后续结果不构成对任何机器的延迟保证。
- Overview 每轮最多推进 8 个解析器，最多保留 20 个；100 ms 是调度预算，已经开始的有界日志批次会完成。当前、选中和需要处理的会话优先，其余轮转；排队或追赶的行显示 `Updating`。同一数据范围、同一 tmux server 复用短期快照。
- 原生 SQLite 同步查询没有强制中断：50 ms 是诊断预算。超时会记录摘要、行数和最多 8 行查询计划，便于定位实际慢查询；doctor 同时提供原生与 CLI 探测耗时、失败次数和解析器数量。

本机 5 个现有 HUD 重载后的检查中，主 pane 进程、焦点和 UI 偏好均保留，doctor 的诊断有效、日志积压为 0。真实数据库曾记录一条约 62 ms 的查询：计划使用 `idx_logs_ts`，随后对近期记录做分组和排序。它没有查询失败，但说明合成 fixture 的 SQLite 耗时不能代替真实历史库的开销。

同轮离线渲染基准中，单会话 5 / 8 / 12 行为 0.0262 / 0.0221 / 0.0220 ms/frame，Overview 为 0.0950 / 0.0915 / 0.0954 ms/frame。四个 32 MiB 日志读取器冷读约 247 ms、未变化复读约 0.08 ms。此处与上方 9 月的历史记录分开保留：没有同一最终 fixture 的旧版本完整运行时对照，不据此宣称整体 CPU 或内存下降百分比。

## 2026-10-29：查询隔离、缓存与基准校正

这轮发现旧运行基准的 `logs` 表仍使用 `message`，而采集器已读取 `feedback_log_body`；仅验证画面出现项目名，会把“总览扫描成功、SQL 全部失败、主会话未绑定”也算作有效运行。因此这轮丢弃该旧 fixture 的运行数字，修正字段和索引，并为模拟的进程内 TUI 加入明确的 app-server 记录。基准现在要求每个 HUD 绑定到自己的会话 ID 和 rollout 路径，且 SQLite 失败数为 0。

同机 macOS arm64、Node v24.21.0；基线提交 `4b7c972` 与修复版使用同一份 fixture v2，顺序运行，每组 12 秒、每日志 8 MiB、59 次追加。测试使用私有 tmux 和合成数据。原始汇总见 [performance-2026-10-29.json](./performance-2026-10-29.json)。

| HUD 数量 | CPU ms：修复前 → 后 | 峰值 RSS 合计 MiB：前 → 后 | 最大事件循环停顿 ms：前 → 后 | 原生 SQL 条数：前 → 后 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 469.71 → 338.27 | 94.77 → 107.30 | 16.39 → 14.72 | 541 → 145 |
| 5 | 3685.30 → 3191.44 | 574.80 → 679.19 | 25.26 → 19.42 | 2722 → 741 |
| 20 | 15853.31 → 17032.62 | 2091.25 → 2403.28 | 43.12 → 37.16 | 11048 → 2845 |

三组均成功绑定，SQL 失败数均为 0。小查询采用进程内有界缓存、同请求合并和最多 750 ms 的短期文件共享；数据库及 WAL 变化使缓存立即失效。共享文件的读取和写入按数据库限频，避免一次查询序列反复序列化相同快照。原生 SQL 执行次数减少约 73%–74%，不会把缓存重用记成已执行的 SQL。

原生 SQLite 改到 Worker，UI 线程不再同步执行语句；8 秒请求期限会放弃该 Worker，等待其退出后才允许替换，防止慢原生调用积累多个后台线程。独立回归通过一百万项递归查询验证：查询尚未完成时，UI 心跳仍继续；同时验证并发同查询合并、WAL 更新失效及数据库替换。Node 20 保留异步 `sqlite3` CLI 后备路径。

这是响应性与资源使用的权衡，不能宣称全面降耗：单次样本的 1／5 HUD CPU 分别下降约 28%／13%，20 HUD CPU 增加约 7%；Worker 使各组峰值 RSS 合计增加约 13%–18%。RSS 包含共享页，峰值相加不是同一时刻的全机峰值；CPU 包括 Worker 线程但不含子进程，且包含启动和持续写入，不代表稳定空闲占用。合成数据库的小查询也不能代表真实大库的最慢语句。

离线渲染仍在每帧约 0.03 ms（单会话）、0.10 ms（总览）的量级；这轮主要解决数据正确性和采集阻塞，没有把微秒级浮动当成渲染优化收益。进程启动时间共享只保存 PID 和启动时间，不保存完整命令行；Linux 仍优先直接读 `/proc`。

部署验证补充：上表对应 `2bf6b91` 的查询实现。Train1009 容器进一步复现了连续 SQLite 提交的 `mtime`、`ctime` 和文件大小完全相同，而数据库变更计数已从 4 增至 5，导致旧缓存返回前一次结果。缓存版本现加入数据库头的变更计数和 WAL-index 的事务头；索引头缺失或两份副本不一致时直接查询，不使用缓存。格式依据为 [SQLite 数据库文件格式](https://sqlite.org/fileformat.html#file_change_counter) 和 [WAL-index 头格式](https://sqlite.org/walformat.html#the_wal_index_header)。回归固定文件时间戳与大小，分别覆盖普通提交和数据库头不变的 WAL 提交。这项加固后的完整性能比例尚未重测，上表不代表加固后的重新测量。

同轮实机重载还发现，长会话的线程外日志被裁剪后，旧版本冷启动也可能误把进程内 TUI 当成 daemon 客户端。现在额外检查该进程近期线程日志中的 app-server 标记，仍要求进程自己的服务端记录作为证据，不依据其他会话的标题或普通 TUI 引用猜测绑定；对应回归从新进程启动，确保不依赖已有内存缓存。

本次样本的 SQL 执行次数减少约 94%–97%，累计 CPU 减少约 23%–35%。这些是包含冷启动和持续追加的单次对照，不代表稳定空闲占用，也不保证其他机器具有相同比例。内存没有下降：20 个进程的峰值 RSS 之和仍约 2.3 GiB，结束 RSS 更高；各进程峰值不是同时发生，RSS 包含共享页。事件循环 p95 略低，但 1 和 20 HUD 的最大停顿变高，不能据此宣称尾延迟改善，也没有足够证据把单次停顿归因于 GC、SQLite 或某个系统调用。
